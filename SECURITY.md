# Security and production limitations

**MVP design, NOT an audited product.** The following are mandatory operational controls, not optional hardening:

1. **Data plane:** Xray SOCKS5 outbounds are not encrypted on their own. Encrypt transport between VPN infrastructure and third-party residential gateway with a private encrypted link/tunnel or a vetted secure proxy transport. Do NOT assume public SOCKS5 is confidential. HTTP proxies are not accepted by this MVP.
2. **Leak model:** Exact-IP probing samples the upstream egress at a point in time. The provider might reassign an address between probes; the controller detects some changes at the next check (normally at most 30 min) and can blackhole only after applying updated Xray settings. A strict continuous fixed-IP service needs a contractual exclusive lease, provider-side binding enforcement, and separate host-level egress restrictions.
3. **Fail-closed:** Active premium users have explicit user-based Xray outbound routing and a UDP blackhole. When observed IP changes/exit fails verification, the next successful reconciliation replaces the route with `RIP_DENY`. If Marzban is unreachable or a configuration apply fails, previously deployed rules remain in effect. Network isolation/firewall enforcement is recommended before claiming zero leaks.
4. **DNS and IPv6:** `socks5` proxy probe resolves destinations remotely, but real client DNS depends on the VPN app, routing and system/browser policies. Detect and prevent client-side DNS, IPv6, QUIC and WebRTC bypass independently. This MVP blocks UDP for premium connections and makes no gaming/VoIP UDP promise.
5. **Marzban:** `/api/core/config` PUT restarts the core **and all connected nodes**. Avoid high-frequency route changes during heavy load. Use maintenance windows for substantial batches and keep original config backed up. For large deployments implement separate premium nodes and staged reloads instead.
6. **Billing:** The add-on accepts only internal signed entitlement events. Stripe or CoinPayments signatures must be checked by a billing processor **before** it calls this add-on. Reject unsigned or unauthenticated grants. If an HMAC event is stored but apply fails, it remains pending/revoking, and periodic reconcile or manual retry is required.
7. **Secrets:** `.env` is private and `chmod 600`; never commit it. Proxy passwords enter Marzban core config via the authenticated sudo API, and therefore can appear in Marzban config backups and internal operational logs. Restrict both systems. Rotate secrets and re-deploy as necessary.
8. **Marzban admin privileges and identity lookup:** Requires a sudo-equivalent Marzban service account to GET/PUT the core config. The public Marzban user response does not expose numeric ID, so this add-on needs a separate, read-only SQL lookup of `users(id,username)`. Never give the SQL identity account INSERT/UPDATE/DELETE permissions. Docker's read-only SQLite mount exposes other data in that directory to the container; for stronger least privilege, put Marzban on MySQL and grant an id/username-only SQL SELECT account. Restrict all connections to a management network.
9. **Inventory accuracy:** Import only approved opt-in residential supply or dedicated ISP products with documented exclusivity and VPN resale rights. `exclusive=true` is an **operator attestation**, not independent proof. A healthy proxy can still be the wrong network class.
10. **Storage and concurrency:** Uses SQLite `BEGIN IMMEDIATE` and a single Docker worker. Never run multiple instances behind a load balancer. Protect the volume, backups and API. PostgreSQL with row locks, migrations and a durable deployment queue is a Phase 2 step.
11. **Review what changes:** The add-on only owns `RIP_`-prefixed outbounds and matching rules. It inserts guards before existing routing rules, which can override original premium-user policies; test and adapt this for any existing geo-blocking/anti-abuse rules. The original nonpremium rules remain in their original order. Raw Xray config contains sensitive credentials and should not be logged.
12. **Limit access:** `/v1/...` is an admin service and must never be exposed publicly. Docker publishes only `127.0.0.1:8787`. If billing runs remotely, connect over authenticated private overlay. Signed webhook is for service-to-service only.

## Major constraints not implemented

- No vendor-independent guaranteed private IP procurement API. No customer-visible subscription UI. No usage-based pricing reconciliation, DDoS resistance guarantees, UDP full-tunnel, persistent zero-downtime Marzban core updates, VPN-client leak audit, live real-Xray integration validation, credential encryption at rest or full security audit.
- HTTPS security between Xray and SOCKS5 provider is NOT provided by Xray SOCKS itself; configure it in your network stack.
- Automatic IP failover without a new customer-facing public IP is impossible without another lease for the same public IP (e.g. provider HA). Fail closed and alert instead of silently changing an advertised dedicated address.
